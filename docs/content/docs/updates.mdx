title: "Updates"
---

Native SDK includes its own signed updater. It does not use Sparkle, Squirrel, or another updater framework: a release is a ZIP archive described by a feed signed with Ed25519, and an installed app verifies the feed with the keys in its manifest before it downloads anything.

Who runs the update depends on the platform:

Apps using the system host (<code>web_engine: "system"</code>).</td>

## Configure the app

Generate an Ed25519 key pair once:

```bash
native update keygen --private-key ~/Documents/my-app-update.key
```

The command writes the 32-byte private seed with mode `0600` and prints the base64 public key. Back up the private key securely and keep it out of the app repository, build artifacts, and update server.

Put only the public key and feed URL in `app.json`:

```json
{
  "$schema": "https://schema.native-sdk.dev/app/v1.json",
  "id": "com.example.my-app",
  "name": "my-app",
  "version": "1.0.0",
  "updates": {
    "feed_url": "https://example.com/releases/{target}/native-update.json",
    "public_key": "base64-ed25519-public-key",
    "check_on_start": true
  }
}
```

Legacy `app.zon` uses the same fields:

```zig
.updates = .{
    .feed_url = "https://example.com/releases/{target}/native-update.json",
    .public_key = "base64-ed25519-public-key",
    .check_on_start = true,
},
```

`check_on_start` checks after launch. With the macOS host's own flow the check is quiet: no-update results stay silent and failures go to the app log. When the app drives updates, it sees the result like any other check's.

`mode` picks who drives updates on macOS: `"host"` (the default) keeps the host's menu item and prompts, and `"app"` turns them off and hands updates to the app through the same requests and channel Windows apps use (see [Drive updates from the app](#drive-updates-from-the-app)). Windows apps always drive updates themselves, whatever `mode` says.

Each installed app expands two placeholders in the path or query of `feed_url` before it checks:

A feed holds the release for one target, so `{target}` lets one manifest serve every build: Apple silicon installs read `releases/macos-aarch64/native-update.json`, x64 Windows installs read `releases/windows-x86_64/native-update.json`, and so on. A `feed_url` without placeholders serves a single target.

Both URLs in the release path—the feed URL and archive URL—must use HTTPS. The Ed25519 signature remains the authority if the server or TLS endpoint is compromised.

## Build the update archive

### macOS

Package the app with the same signing identity as the installed release and request the updater ZIP:

```bash
native build
native package \
  --target macos \
  --signing identity \
  --identity "Developer ID Application: Your Name (TEAMID)" \
  --update-archive
```

The command emits the `.app` and a ZIP named like:

```text
zig-out/package/my-app-1.1.0-macos-ReleaseFast-update.zip
```

That ZIP contains exactly the packaged `.app`. Do not use the user-facing DMG as the update archive. When the manifest enables updates, `zig build package` also requests this updater ZIP automatically; use the direct `native package` command when you need Developer ID signing flags.

### Windows

Package the app with the setup program for new installs and the update archive for existing ones:

```bash
native build
native package --target windows --installer --update-archive
```

Beside the artifact directory, the command writes:

```text
zig-out/package/my-app-1.1.0-windows-x86_64-setup.exe
zig-out/package/my-app-1.1.0-windows-x86_64-update.zip
```

The update archive is the same install image the setup program carries. Code-sign `zig-out/bin/my-app.exe` before `native package` so both carry the signed executable. When the manifest enables updates, `zig build package` on Windows requests both.

## Sign the release feed

Upload the ZIP to its final HTTPS URL, then sign its immutable URL, size, digest, app identity, version, target, and release notes:

```bash
native update sign \
  --manifest app.json \
  --private-key ~/Documents/my-app-update.key \
  --archive zig-out/package/my-app-1.1.0-macos-ReleaseFast-update.zip \
  --url https://example.com/releases/my-app-1.1.0-macos-aarch64.zip \
  --target macos-aarch64 \
  --notes "Faster launch and improved export reliability." \
  --output native-update.json
```

Use `macos-aarch64` for Apple silicon, `macos-x86_64` for Intel, `windows-x86_64` for x64 Windows, and `windows-aarch64` for Arm64 Windows. Publish the resulting `native-update.json` at the manifest's `feed_url` with `{target}` replaced by that target. Sign and publish one feed per target.

`native update sign` refuses a private key that the manifest does not trust (its `public_key` or one of its `public_keys`), and refuses an archive whose executable does not contain the architecture named by `--target`. A Windows archive must be the install image `--update-archive` wrote for this app and version.

Installed apps ignore feed fields they do not know, so later SDK versions can add fields to the feed without breaking existing installs. Apps built with SDK versions up to `0.11.0-fork.3` reject unknown fields; keep their feed URLs serving feeds signed by those versions.

## Rotate the update key

Installs verify a feed against every key their manifest trusts: `public_key` plus up to three `public_keys`. To move to a new key without stranding existing installs:

1. Generate the new key with `native update keygen`.
2. In the next release, set `public_key` to the new key and add the old key to `public_keys`.
3. Sign that release's feed with the old key, which the previous release already trusts.
4. Sign later releases with the new key, and drop the old key from `public_keys` once no supported install depends on it.

```json
"updates": {
  "feed_url": "https://example.com/releases/{target}/native-update.json",
  "public_key": "base64-new-public-key",
  "public_keys": ["base64-old-public-key"]
}
```

A lost private key cannot be rotated away from: installs that trust only that key cannot verify any later release. Keep a backup of every private key a supported release trusts.

## Trigger a check on macOS

With the host's own flow (`mode` left at `"host"`), the stock application-menu item requires no app code. To place the action in another menu, tray item, shortcut, or native control, dispatch the reserved command:

```text
app.check-for-updates
```

The runtime consumes this command as a host action. Do not map it through a TypeScript core's `commandMsg` or a Zig app's `on_command`.

## Drive updates from the app

On Windows, and on macOS with `"mode": "app"`, the updater shows no UI and never quits the app on its own. The app sends requests and follows a channel; what to show, when to download, and when to restart are the app's decisions.

Every request takes an empty payload and answers at once. `status` answers the current status and `notes` the release notes; the other requests answer an empty `ok` once accepted, and checks and downloads then run in the background. The `err` arm receives `unsupported`, `busy`, `not_available`, `not_ready`, `not_downloading`, `invalid_request`, or `restart_failed`.

The `native-sdk.updates` channel source, opened with empty arguments, delivers the current status when it opens, then a status at every change and about every percent of a download, in the order they happened. Follow the channel to keep a status current; a `status` answer is a one-off read. A status is UTF-8 lines of `name value`:

Read lines by name: later SDK versions may add lines. A TypeScript core opens the channel from `initialModel` and turns presses into requests:

```ts:src/core.ts
import { Cmd, asciiBytes } from "@native-sdk/core";

export type ChannelState = "data" | "closed" | "rejected";
export type ChannelSourceState = "started" | "skipped" | "failed";

export interface Model {
  readonly updateStatus: Uint8Array;
}

export type Msg =
  | { readonly kind: "updatesOpened"; readonly key: number; readonly state: ChannelSourceState; readonly bytes: Uint8Array }
  | { readonly kind: "updatesChanged"; readonly key: number; readonly state: ChannelState; readonly bytes: Uint8Array; readonly droppedPending: number; readonly droppedTotal: number }
  | { readonly kind: "updateAccepted"; readonly body: Uint8Array }
  | { readonly kind: "updateRefused"; readonly reason: Uint8Array }
  | { readonly kind: "checkForUpdates" }
  | { readonly kind: "downloadUpdate" }
  | { readonly kind: "restartToUpdate" };

export function initialModel(): [Model, Cmd<Msg>] {
  return [
    { updateStatus: new Uint8Array(0) },
    Cmd.channelOpenSource(1, "native-sdk.updates", new Uint8Array(0), { event: "updatesChanged", started: "updatesOpened" }),
  ];
}

export function update(model: Model, msg: Msg): Model | [Model, Cmd<Msg>] {
  switch (msg.kind) {
    case "updatesOpened":
      return model;
    case "updatesChanged":
      return msg.state === "data" ? { ...model, updateStatus: msg.bytes } : model;
    case "updateAccepted":
    case "updateRefused":
      return model;
    case "checkForUpdates":
      return [model, Cmd.request("native-sdk.updates.check", new Uint8Array(0), { ok: "updateAccepted", err: "updateRefused" })];
    case "downloadUpdate":
      return [model, Cmd.request("native-sdk.updates.download", new Uint8Array(0), { ok: "updateAccepted", err: "updateRefused" })];
    case "restartToUpdate":
      return [model, Cmd.request("native-sdk.updates.restart", new Uint8Array(0), { ok: "updateAccepted", err: "updateRefused" })];
  }
}

// The value of one `name value` line of a status; empty when absent.
function statusLine(status: Uint8Array, name: Uint8Array): Uint8Array {
  let start = 0;
  while (start < status.length) {
    let end = start;
    while (end < status.length && status[end] !== 10) end += 1;
    if (end - start > name.length && status[start + name.length] === 32 && startsWithAt(status, start, name)) {
      return status.subarray(start + name.length + 1, end);
    }
    start = end + 1;
  }
  return new Uint8Array(0);
}

function startsWithAt(bytes: Uint8Array, at: number, prefix: Uint8Array): boolean {
  for (let i = 0; i < prefix.length; i++) {
    if (bytes[at + i] !== prefix[i]) return false;
  }
  return true;
}

export function updateState(model: Model): Uint8Array {
  return statusLine(model.updateStatus, asciiBytes("state"));
}

export function updateVersion(model: Model): Uint8Array {
  return statusLine(model.updateStatus, asciiBytes("version"));
}
```

A staged release waits in `ready` until the app asks to restart, and otherwise:

- On Windows it applies at the next launch: the launcher the setup program installed moves it into place before it starts the app, whichever way the app is opened (Start menu, a document, a link).
- On macOS it installs when the app quits normally: a helper replaces the `.app` once the process has exited, without reopening it. A release staged before a crash or a forced quit stays `ready` at the next launch and installs at the next quit.

After `restart`, the helper waits up to a minute for the app to exit; an app that does not quit keeps running, and its release applies as above.

## Test an update locally

Set `NATIVE_SDK_UPDATES_FEED_URL` to test an update end to end without publishing it: an installed app started with the variable checks that URL instead of the manifest's, and accepts loopback `http://` URLs for the feed and the archive. The manifest's keys still decide what installs.

```bash
native update sign \
  --manifest app.json \
  --private-key ~/Documents/my-app-update.key \
  --archive zig-out/package/my-app-1.1.0-windows-x86_64-update.zip \
  --url http://127.0.0.1:8080/my-app-1.1.0.zip \
  --target windows-x86_64 \
  --allow-loopback-http \
  --output test-feed/windows-x86_64/native-update.json
```

Serve `test-feed`, with the archive at `my-app-1.1.0.zip`, on `127.0.0.1:8080`, then start an installed earlier version with `NATIVE_SDK_UPDATES_FEED_URL=http://127.0.0.1:8080/{target}/native-update.json`. Loopback hosts are `127.0.0.1`, `[::1]`, and `localhost`; `native update sign` refuses an `http://` archive URL without `--allow-loopback-http`, and installed apps refuse one unless the variable is set.

## Verification model

The updater verifies every release in this order:

1. Decode the bounded feed envelope.
2. Verify its exact payload bytes with one of the app's trusted Ed25519 public keys.
3. Match bundle ID, target, and a newer semantic version.
4. Download through HTTPS and reject redirects away from HTTPS.
5. Match the signed archive byte size and SHA-256 digest before extraction.

On macOS it then:

6. Requires exactly one top-level `.app` with the expected bundle ID and version.
7. For Developer ID apps, requires the update to retain the installed app's bundle identifier and Apple signing team.
8. Exits the app, replaces it in the containing directory, retains the old bundle as rollback, and relaunches.

With `"mode": "app"`, steps 6 and 7 run when the release is staged, beside the app in a hidden `.<App>.app.native-update` folder. Step 8 runs when the app restarts into the release, or, without relaunching, when it quits.

On Windows it then:

6. Unpacks the archive into `app.next\` beside the installed `app\`, and requires its install configuration to name this app, the signed version, and the same executable, built for this architecture.
7. Marks the staged copy complete. With nothing running from `app\`, the launcher renames `app\` to `app.prev\` and `app.next\` to `app\`, and a launch after an interrupted switch finishes or reverts it.

Unsigned and ad-hoc apps can use the Ed25519 trust path for development. Public releases should still be Developer ID signed and notarized so Gatekeeper can identify the developer and validate the downloaded app independently.

## Current limits

- macOS: the containing directory must be writable by the current user. The updater does not request administrator privileges or install into an administrator-owned location. A quarantined app running from a translocated copy updates only after the user moves it, for example into Applications.
- Windows: only apps installed per user by the SDK's setup program update; a development build or a copied folder reports `not_installed`. The updater does not check the Authenticode signature of a release, and the previous version stays in `app.prev\` without an automatic rollback.
- The macOS Chromium host and Linux are pending.
- Full ZIP releases are supported. Delta updates, channels, phased rollout, skipped-version preferences, and automatic background installation are not implemented yet.
- An app renamed in Finder is supported; the update ZIP may keep its original bundle filename.
