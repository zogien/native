---
title: "Data Directory"
---

Every path where the SDK keeps an app's data comes from one place, resolved once when the app starts. That covers the six app directories (`data`, `config`, `cache`, `state`, `logs`, `temp`) and the stores in them (`store.db`, `app.db`, `snapshot.nsd`). It also covers the window-state file, the logs, the URL media cache, the working directory of [TypeScript services](/docs/typescript/services), and the web engine profile. By default these paths follow the platform conventions below. One launch flag moves all of them under a directory you choose.

The macOS CEF profile is per app. SDK versions before this one kept every CEF app's profile in one shared `~/Library/Application Support/native-sdk/CEF` folder; that folder is no longer used and can be deleted. iOS and Android keep their apps' sandbox containers (see [Embed](/docs/embed)).

## Choosing a data directory

Pass the root on the command line, or set the environment variable:

```bash
my-app --native-data-dir=./profiles/work
my-app --native-data-dir ~/profiles/work
NATIVE_SDK_DATA_DIR=/tmp/try-it native dev
```

A relative path resolves against the working directory of the launch. The directory and its parents are created if missing, and the app uses the directory's canonical absolute path, so two spellings of one folder name the same data directory: symlinks and `..` are resolved, and on Windows the path takes the folder's long names and on-disk case. The SDK does not expand `~`; your shell does.

An unusable root ends the launch before any window opens, with exit code 2 and a message on stderr that names the problem. The app never falls back to the default directories behind it. A root is unusable when:

- the path is empty, or the flag has no path or appears twice;
- the path, or a folder on the way to it, is a file;
- the directory cannot be created, for example under a read-only parent;
- its absolute path is longer than 960 bytes;
- one of its layout folders cannot be created in it.

The six directory folders are created at launch; `legacy-data/` and `webview/` when first used. A root belongs to one app: the folders carry no bundle id, so two different apps pointed at one root would share it.

## Web engine profile

Each root gets its own web profile, so launches with different roots share no cookies, web storage, or caches:

- **WebView2** keeps its user data folder in `webview\`. The legacy `<exe>.WebView2` folder beside the executable (see [Web Engines](/docs/web-engines)) only ever moves into the default folder, never into a root.
- **CEF** on macOS uses `webview/` as its root cache path.
- **WebKitGTK** uses a network session of its own, with website data in `webview/data/` and caches in `webview/cache/`.
- **WKWebView** on macOS 14 and later uses a persistent data store keyed by an identifier derived from the root, so the same root reopens the same store. WebKit keeps that store in its own location under `~/Library/WebKit/` (`<app>/WebsiteDataStore/<identifier>`, where `<app>` is the bundle id of a packaged app), not in the root. Before macOS 14, WKWebView offers no such store: every root shares WebKit's default data store, and the app prints a warning at startup.

## What stays outside the root

- Credentials live in the OS credential store (Keychain, Credential Manager, Secret Service), keyed by the app's identity, so every root sees the same credentials.
- App-driven updates belong to the installation. Their downloads and install scripts use the OS temporary directory, and the macOS install result stays in the default `data` directory. The relaunch after an update passes the app no arguments, so a root given with the flag is not carried over. On Windows the relaunch inherits the environment, `NATIVE_SDK_DATA_DIR` included; on macOS it goes through Launch Services and inherits neither.
- One-off temporary files the hosts write for themselves (CEF's pages loaded from HTML strings) stay in the OS temporary directory.
- Session recordings go wherever `NATIVE_SDK_SESSION_RECORD` names.
- `native db status` and `native db reset`, and the `native dev --core` logic loop, work on the default `data` directory.

## Arguments the app sees

The flag is the SDK's, not the app's. The SDK removes `--native-data-dir`, and the path that follows it in the two-argument form, everywhere it reports launch arguments to the app: in the launches a [single-instance](/docs/app-zon) app receives on `native-sdk.app.launches`, and in `NATIVE_SDK_ARG_1`. Arguments after `--` are always the app's. A Zig app that reads `init.minimal.args` itself sees the raw arguments; `native_sdk.app_dirs.app_data.ArgumentFilter` drops the flag the same way.

## Single instance

An app with [`single_instance`](/docs/app-zon#single-instance) has one owner per data directory, per user and login session:

- Without an override, the owner is per app, keyed by the bundle id as in earlier versions. A copy of an older version that is still running and a newly started newer version find each other during an upgrade.
- Launches with different roots run side by side, each owning its own root.
- A later launch with the same root, under any spelling of it, hands its launch to the process that owns that root and exits.
- Ownership follows the data directory a launch actually uses. A root whose `data` folder is the default data directory shares the default owner. On Windows that is a root at `%LOCALAPPDATA%\<bundle-id>`, whose `data`, `cache`, `state` and `logs` folders are the default ones. Any other root never shares an owner with a launch on the default directories.

The root alone keys ownership, as it keys the folders: another `single_instance` app launched on a root that an app already owns hands its launch to that app.

Ownership is implemented on Windows. macOS and Linux run without it for now. On Linux, the GTK host also folds every later launch of a bundle id into the process already running it, even with a different root, so two roots of one app cannot run side by side there yet.
